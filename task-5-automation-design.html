Task 5 — Design of the monthly-close automation

Brief: monthly close is currently two days of manual work (statement download → categorise → match invoices → chase missing → create top-up tasks → draft principals summary). Stack: Claude (Cowork + Code), self-hosted n8n on a UAE-region VPS, Google Workspace, Todoist. Below is the proposed pipeline, Mermaid architecture diagrams, approval gates, failure modes, security posture, and the verbatim first prompt.
Stack decision: switch Make.com to self-hosted n8n on a UAE-region VPS. The cost is roughly equal once you factor in maintenance time, but bank statements, IBANs, and payroll files stop leaving our perimeter, we own the audit trail, and we stop being subject to a third-party SaaS's retention policy, pricing changes, or acquisition risk. Given the BEC attempt and the early-paid AED 93,750 cheque we saw this quarter, the control argument outweighs the convenience of a hosted UI.

Stack rationale per layer

  • n8n on UAE VPS is the orchestration layer. It runs cron schedules, webhooks, retries, error branches, and calls downstream tools. Hosting on the UAE VPS means statements and IBANs never leave our perimeter and we keep a full execution log on disk under /var/log/n8n/.
  • Claude Cowork handles the AI steps (3, 4, 5, 7) via n8n's HTTP Request node hitting the Anthropic API. The chart of accounts and the vendor master Sheet are loaded as Cowork skills, so the prompts are deterministic across runs.
  • Claude Code is reserved for building the pipeline itself, the Cowork skill definitions, and the vendor master Sheet validator — i.e. engineering work, not production traffic.
  • Google Workspace stays the system of record. All outputs land in Drive / Sheets / Docs / Gmail, so the AI layer is replaceable without data migration.
  • Todoist is used as-is for human task tracking; we do not replace it with anything.

The deciding factor is the BEC attempt and the early-paid AED 93,750 cheque seen this quarter (Task 4). Once the principal has seen a real attack and a real loss, the calculus on a hosted automation UI changes: control outweighs convenience.

5 — Three most likely failure modes and mitigations

#Failure modeDetectionMitigation
F1Mis-parsed PDF (multi-page statement split, columns misaligned).n8n step 2 sanity check: parsed row count ≥ raw page count × min-rows-per-page. Alert if < 80%.Fallback to pdfminer.six on the VPS. If that also fails, n8n workflow pauses and raises a Todoist task; it never proceeds with bad data.
F2Hallucinated category or vendor name.Every row carries the original line_snippet from the PDF and a confidence score. Rows where confidence < 0.7 highlighted amber at G2.Chart-of-accounts prompt forbids inventing categories; new vendors must be added to the master Sheet first, so "UNKNOWN" is a deliberate signal, not a hallucination slot.
F3Vendor chase email to the wrong vendor (BEC-style).Vendor master Sheet is the single source of truth for name, address, TRN, default contact. Cowork is forbidden from inventing addresses.Draft sits in Gmail Drafts; human opens it and visually confirms the To: line at G4. If the master Sheet does not contain the vendor, step 5 produces a draft addressed to "VENDOR-ON-FILE-MISSING" and raises a Todoist task. No email is sent to an address that does not appear in the master Sheet.

6 — What I would NEVER automate end-to-end

Hard rule: the AI never initiates a payment, signs off a reconciliation, or sends an email without a human click.
  • Payments. The AI may draft a payment instruction, but the actual click on the bank portal must be a human. A wrong auto-payment is immediate, irreversible cash-out. There is no amount threshold below which this is acceptable.
  • Reconciliation sign-off. The AI produces the reconciled balance and a list of reconciling items. The counter-signature is always a human. Reason: audit trails require a named approver who has read the reconciliation, not an AI agent that produced it.
  • Sending emails to vendors. Drafts only. Reason: vendor email compromise is a top fraud vector in the UAE (D9 in our Task 4 register); the AI cannot tell a genuine vendor email from a typosquatted one at send time.
  • Anything touching external bank APIs with write access — read-only balance and statement pulls via OAuth-scoped credentials only.

One-sentence vetting rule before connecting any AI tool: read its data-handling and training policy, confirm it offers a no-train / zero-retention mode for Workspace data, and refuse to connect any tool that retains prompts or outputs on its own infrastructure for model improvement.

8 — Verbatim first prompt for the n8n build (step 1, statement ingestion)

You are building step 1 of the monthly-close pipeline for Quant Lab family office, a DMCC free-zone entity. This skill runs inside our self-hosted n8n on a UAE-region VPS at /var/n8n/data/finance/. The orchestrator is n8n, not Make.com; treat the Make.com references in any prior docs as superseded. Trigger: cron schedule firing on the 1st of every month at 07:30 UAE time, set up in the n8n workflow definition file workflow_01_ingest.json. Inputs the n8n workflow already has wired: - A Gmail OAuth credential authorised under the operator's Workspace account. - Google Drive with /Finance/Statements/YYYY-MM/ (created if missing) and /Finance/Close_Log/. - A Todoist API token for the operator's project Finance / Top-ups. - A vendor master Sheet called /Finance/_config/Vendor_Master listing the canonical account numbers we expect statements for. The three we always expect are: ACCT 3510 (operating account), CARD 1346 (corporate card primary), CARD 0951 (corporate card secondary). For now, ignore any statement that does not match these three. The skill's job in this step is to collect the statements. Specifically: 1. Use the Gmail node to search for unread emails received since the 1st of the current month from the bank (sender matches the configured bank-sender pattern) and the known card issuers, where the email has a PDF attachment. 2. For each PDF, save it to /Finance/Statements/YYYY-MM/ with filename pattern <ACCOUNT>_YYYY-MM.pdf. Use the account number parsed from the PDF first page if the email subject or attachment filename does not already match. 3. After all statements are filed, append one row to /Finance/Close_Log/YYYY-MM with columns: timestamp (now ISO8601), expected_count (3), received_count, missing_accounts (list or 'none'), notes (free text). 4. If any of the three known accounts is still missing after 24 hours of waiting, use the Todoist node to create a task in project 'Finance / Top-ups': title 'Chase missing statement for <ACCOUNT> for YYYY-MM', due today, assigned to the operator. Hard rules for this step: - Do NOT parse the PDF contents. That is step 2 and belongs to a different n8n workflow file. - Do NOT send any email. Chase emails for missing statements are step 5 and require a human click. - Do NOT initiate any payment or contact any vendor beyond the Todoist task in rule 4. - If a PDF arrives that matches none of the three known account numbers, save it as UNKNOWN_YYYY-MM_seqN.pdf and flag it in missing_accounts with a note. Do not silently drop it. - Every action must log to /var/log/n8n/finance/ingest-YYYY-MM.log with: timestamp, action, target, result, error if any. The audit trail stays with us on the VPS. Output: three (or four including unknown) standardised PDFs in /Finance/Statements/YYYY-MM/, exactly one row in /Finance/Close_Log/YYYY-MM, zero to three Todoist tasks, and a structured execution log entry. Nothing else.

9 — Honesty question

I have used Claude Code extensively to build and run the local AI agent orchestration stack under C:/My_youtube_channel/rams_lab_silent_killer — the hierarchical orchestrator with persistent memory that I have been operating for months.

One concrete example: in mid-2026 I asked Claude Code to refactor the orchestrator's prompt-assembling function so it would fall back gracefully when memory lookups returned empty, rather than emitting the literal string "(No prior context recalled — this may be a new topic.)". The agent produced a working refactor across roughly 400 lines that correctly handled the empty fallback. I had to fix three things before it shipped: (1) it left a stale reference to a removed import that broke the build on first run; (2) it placed the new fallback branch in the wrong function — it modified the memory query helper instead of the prompt builder that consumed the result; (3) it duplicated an existing constant rather than reusing the one defined in the constants module. Net: Claude saved about an hour of careful editing, I spent about 15 minutes fixing — net positive, but two of the three fixes would have silently produced wrong output in production, which is why the prompt above insists on line_snippet, confidence and the vendor-master Sheet as ground truth.

On n8n specifically: I have not yet stood up an n8n instance for monthly close, but the same running stack does operate an n8n instance at n8n.sgctech.ai for a separate workflow, so the failure modes described above (n8n instance errors during scheduled runs, hardcoded credentials inside HTTP Request nodes) are ones I have personally fixed and would build the right guardrails against on first deployment.
